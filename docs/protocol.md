# Air75 HE protocol observations

Inspected on 2026-11-03:

- Official app: <https://drive.nuphy.io/>
- Shipped bundle: <https://drive.nuphy.io/static/js/main.ba072d08.js>
- Bundle SHA-256: `df67fad34982ebdbcc9b74dec4912cc5079f4ce782a1166974ddb8d06f0fba32`
- Linux userspace LED API: <https://docs.kernel.org/leds/uleds.html>
- Related virtual-backlight design: <https://github.com/paco3346/fw16-kbd-uleds>

These are observations from static JavaScript inspection and isolated execution
of command/serialization functions in a Node VM with browser/network behavior
stubbed. They are not hardware captures or REA Evidence records. REA tools and
CLI were unavailable in the session; ordinary local inspection supplied these
findings. The vendor bundle is not distributed with this project.

The app's supported-device table lists vendor `6645` (`0x19f5`), product `24864`
(`0x6120`) as Air75 HE. Local sysfs confirms the product name and exposes three
HID interfaces. `input1` has an unnumbered input/output collection with 64-byte
reports and usage page 1 / usage 0. The executable checks its exact descriptor
as well as VID/PID before sending commands.

The HE implementation is `Pt` inside webpack module `86736`; its lighting
serializer is `ne`. The newer non-HE implementation `Ln` has a different
protocol and is not used here. `Pt` constructs `ne` as its lighting data handler.
The app's `createCommand` function produces these 64-byte packets:

| Byte | Meaning |
| --- | --- |
| 0 | Request `55`, response `aa` |
| 1 | Command |
| 2 | Key, zero for these HE operations |
| 3 | Sum of bytes 4–63, modulo 256 |
| 4 | Data length, up to 56 |
| 5–6 | Little-endian address |
| 7 | Reserved, zero |
| 8–63 | Data, zero-padded |

The WebHID call is `sendReport(0, report)`. Linux hidraw writes require an extra
leading report-ID byte `00`, making each write 65 bytes. Reads are 64 bytes
because this collection has no numbered report ID.

`GetBase` (`04`), length 16 at address 0, returns the current mode in payload
byte 0 for Air75 HE. The app's model/version offset selector returned zero for
this model at tested version inputs 0, 1, 100, 1000 and 10000. `GetFunc` (`05`)
reads 54 bytes from `mode * 64`; the main brightness is payload byte 9.
The serializer returns `{offset: 9, data: [value]}` for
`serializePartialLightData({brightness: value}, "main")`.
`setLightState` adds `mode * 64` to that offset and invokes `SetFunc` (`06`).
Thus a one-byte write at addresses 9, 73, or 137 changes main brightness for
modes 0, 1, or 2. It does not serialize or overwrite other lighting fields.

Examples generated by those vendor functions (trailing zeros omitted):

```text
GetBase, length 16:              55 04 00 10 10 00 00 00
GetFunc, mode 1, length 54:       55 05 00 76 36 40 00 00
Set brightness 37%, mode 1:      55 06 00 6f 01 49 00 00 25
```

The daemon additionally validates response marker, command, key, checksum,
length, address and reserved byte, and reads back the level after a write.
Invalid modes and brightness values fail closed. Firmware variations may
require different validation or offsets; the real hardware probe is still
required. The daemon does not send guessed V2/V3 commands, firmware commands,
factory resets, keymap writes or color changes.

## Effects and explicit off

The HE enum (`To` in webpack module `93158`) defines lighting effects 0–22,
including Static 3, Breathing 4 and Wave 6, and **OFF_MODE = 255**.
The `ne` serializer puts the main effect at offset 8 and brightness at offset 9.
Calling its partial serializer with `{mode: 255, brightness: 0}` merges those
adjacent fields into a two-byte write. For keyboard profile 1:

```text
Explicit off: 55 06 00 49 02 48 00 00 ff 00 (zero-padded to 64 bytes)
```

The update sends this explicit off at 0%, since a brightness byte of zero alone
did not extinguish the user's keys. The previous effect is saved per profile
before switching off, and restored with the requested brightness when increased.
The save is written atomically in the service's systemd StateDirectory. The new
firmware behavior is source-derived and tested with an emulator; physical
confirmation remains necessary. Choosing an effect while off uses brightness 50.

The virtual LED has max brightness 100. UPower discovers it by the
`::kbd_backlight` suffix, and PowerDevil exposes its standard keyboard slider.
When the hardware level changes, the daemon updates sysfs and asks UPower to
publish that level through this LED's individual D-Bus object. Legacy UPower's
single shared object is used only if this is the sole keyboard LED. UPower may
require a restart after the virtual LED is created; the installer does this.
